# Bill AI Agent — Project Status

Status prepared 2026-10-27; last updated 2026-10-28 after the final demo audit (invoice history, CSV exports and column mapping, dashboard redesign, automatic status re-check, and five live workflow runs). This document distinguishes repository tests and local workflow exports from live production behavior.

## 1. Project Overview

Billflow is a local proof of concept for uploading an invoice, extracting its details, reviewing and correcting the results, then downloading a CSV or sending approved data to n8n and Google Sheets. It is not an accounting or tax-compliance system.

The browser UI is vanilla HTML, CSS, and JavaScript. The server is a dependency-free Node.js HTTP application (Node.js 20+). Invoice processing uses n8n, a Gemini extraction node, and Google Sheets. The project is configured as an ES module package and uses Node's built-in test runner.

## 2. Current Architecture

1. The dashboard in `public/` accepts JPG, PNG, WebP, or PDF files up to 10 MB.
2. `POST /api/extract` validates the request and file signature, creates a submission ID, and forwards the file to the configured n8n webhook. The active n8n export contains the Gemini extraction and invoice-processing nodes; the server does not call Gemini from this upload handler.
3. The n8n workflow formats extracted data, validates totals and line items, checks for duplicates, and writes invoice/review rows to Google Sheets.
4. The dashboard can request `GET /api/submissions/:submissionId/status`. The server calls the status webhook and normalizes its response; the browser receives no n8n authentication secret.
5. `POST /api/csv` normalizes invoice data and returns an escaped CSV. `POST /api/save` validates an approved invoice and forwards it only to a localhost n8n URL.
6. The status UI restores saved fields and line items, and supports a manually entered submission ID. The browser stores the last submission ID in local storage.
7. Invoice history (`server/history.js`) is a local JSON file (`data/invoices.json`, or `BILL_AI_HISTORY_FILE`). The status route records found, non-duplicate invoices; `POST /api/save` records the approved invoice before forwarding it to n8n. `GET /api/invoices` lists summaries; `POST /api/invoices/csv` exports all invoices (no `ids`) or the given `ids` (selected or single). Writes are serialized and atomic (temporary file + rename); a corrupt file causes an error instead of being overwritten.

The server binds to `127.0.0.1` by default. Configuration is documented in `.env.example`; secret values must remain server-side.

## 3. Completed Features

- Upload validation for supported image/PDF types, size limits, and file signatures.
- n8n-based invoice extraction, item formatting, arithmetic validation, and duplicate lookup in the exported workflow.
- Numeric normalization for supported currency-formatted strings, separators, signed amounts, and `hrs` quantities. The existing validation warnings remain for invalid values and mismatched arithmetic.
- Invoice totals and line items, including discount, round-off, currency symbol, and GST percentage when supplied by the extraction.
- Review/edit UI, explicit approval checkbox, warning display, CSV download, and optional n8n save.
- Submission IDs generated by the server for browser uploads; n8n preserves that ID on its webhook path and has a fallback ID on the form-trigger path.
- Status response normalization, restoration by stored or manually entered submission ID, and explicit duplicate-result handling in the server and dashboard.
- CSV formula-injection escaping.
- Invoice history panel with refresh, per-row selection, select-all, and CSV download for all, selected, or one invoice. Each line item is a CSV row. Records persist across uploads and server restarts and are deduplicated by submission ID (or supplier + invoice number for approvals without one).

These are implemented in code or present in workflow exports; live deployment and end-to-end operation are not thereby verified.

One normal run took about 6 minutes in n8n, which led to the 7-minute polling window. These runs were not repeated during the audit.

No supported tax, discount or round-off rule reconciles the rows with the summary, so the warnings are correct and validation was not changed. A reviewer can approve it after checking.

## 5. Known Issues / Pending Verification

No demo blockers are known. Remaining limitations:

- **Polling after reload:** Reloading the page makes one status check for the stored submission ID and does not resume automatic polling. Runs longer than 7 minutes end on **Still processing**; **Restore invoice** checks again.
- **Flagged source bills:** Bills whose printed summary does not match their line items (for example `NS-2026-7318`, above, or the synthetic `ECO-2026-0824` fixture) are correctly flagged for review. Validation does not guess undocumented tax or charge rules.
- **History coverage:** History records only invoices the dashboard looked up as saved, or that were approved with **Send to n8n**. **Download CSV** in the review step does not add to history, and invoices processed only in n8n/Sheets are not imported. If a status lookup finds only an Invoice Reviews row (no line items), nothing is recorded (regression test in `server/history.test.js`).
- **Browser test location:** The Playwright browser suites (history, UI, CSV mapping, polling) live outside the repository; `npm test` covers the logic but not the DOM wiring.
- **WebKit phone emulation:** An intermittent crash on the first 320 px mobile-emulated page in Playwright's WebKit build remains unconfirmed and is not attributed to Billflow (see section 7).

The submission ID `sub-1792746870954-svpovbjnuh` appears in dashboard recovery tests and was used as a manual recovery example. Its presence in tests does not establish that a corresponding live invoice row is available.

**Gemini failure recovery (prepared 2026-10-29; manual n8n setup required).** Before this change, when the Gemini node failed after its 3 tries (2 s apart), the n8n execution stopped before any Sheets write. The status workflow could only report "no rows yet", so the dashboard showed `processing` for its full 7-minute window, then **Still processing**, and a manual re-upload started another long wait. Two edited exports sit next to the originals in `~/Downloads/Extra/AI_imgs/bill-flow/` (the originals are unchanged):

- `Bill AI Agent - Demo (failure recovery).json`: on `02 - Extract Invoice with Gemini`, Retry On Fail is set to 5 tries, 5000 ms apart, and On Error to *Continue (using error output)*. The error output goes to a new `02F - Record Extraction Failure` node, a copy of the existing duplicate-marker node, which appends to **Invoice Reviews** a row with `submission_id`, `review_status = Extraction Failed`, `validation_status = Failed`, and the error text in `review_notes`. No invoice rows are written. Every other node and connection is identical.
- `Bill AI Agent - Submission Status (failure recovery).json`: in `Build Submission Status`, rows marked *Extraction Failed* are ignored for normal results. When they are the only rows for an ID, the workflow returns `found: false, state: 'failed'` with the error text. Saved and duplicate results are unchanged.

Apply both in n8n by hand (edit the two nodes and add the one node, or import and swap), then save and activate. They have been checked only with mocked data, not in n8n Cloud.

The dashboard treats `failed` as final. It re-sends transient failures (503/429/overloaded/timeout/connection errors) automatically after 30 s and then 2 min, each time with a new submission ID, and shows other failures as **Extraction failed** with a **Retry** button. Without the n8n changes, the dashboard behaves as before.

`n8n/WORKFLOW.md` documents a separate local example workflow. It is setup guidance, not evidence that the exported Cloud workflows are deployed.

## 8. Current Limitations

- Local demo/prototype; no user login, roles, or multi-user isolation.
- No application database. Invoice history is a single local JSON file for one server process. It has no delete, edit, search, paging, or retention policy, and anyone who can reach the server can see and export all of it. Submission-ID recovery still depends on the browser-held ID plus status data from n8n/Sheets.
- CSV column mapping can choose, order and rename the 13 default fields plus a line number. GSTIN, payment mode, and per-item GST % are not exported. CSV presets live only in each browser's localStorage.
- External services and credentials are required for extraction and sheet writes.
- No accounting/tax compliance guarantee. Human review is required.
- Not production-ready for public hosting without authentication, secure storage, access controls, privacy review, deployment hardening, monitoring, and verified webhook protections.
